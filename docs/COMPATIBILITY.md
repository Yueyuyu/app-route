# 多客户端与通用代理兼容性

## 不需要限定某个图形客户端

AppRoute 需要可执行分流的后端，而不一定需要一个特定图形应用。独立运行的代理内核也可以成为后端，前提是有可用的控制方式、进程/流量信息以及明确的配置所有者。

首版目标是通过 Clash Party 使用其 Mihomo 内核。未来可以接入其他 Mihomo 客户端或独立内核，但控制 API 相似不等于配置保存方式相同。

## 两条兼容路线

### 路线 A：使用现有内核的分流能力（首版）

应用流量 → 现有接管机制 → 内核的应用规则 → DIRECT 或明确代理出口。

Mihomo 提供 `PROCESS-NAME`、`PROCESS-PATH` 等规则，sing-box 提供 `process_name`、`process_path` 等条件。具体识别能力受操作系统、权限、接管方式和配置影响，不能仅因文档存在字段就承诺本机可用。

对其他 Mihomo 客户端，运行控制代码可复用；配置保存、订阅更新及重启逻辑仍要逐个验证。对 sing-box，需要独立处理规则格式、控制范围和配置持久化，不能将 Clash API 兼容当成完整管理兼容。

### 路线 B：通用代理端口 + 接管组件（后续预研）

应用流量 → AppRoute 管理的接管组件 → 用户提供的 HTTP / SOCKS5 端口 → 对方出口策略。

这条路线可减少对代理客户端品牌的依赖。ProxyBridge 的公开设计展示了“应用规则 + HTTP/SOCKS5 服务器”的可行组合，但 AppRoute 尚未集成它，也未选定底层组件或分发方案。

端口本身不能告诉操作系统“只把某个应用送进来”。如果目标应用自己支持代理设置，可以单独配置它；要统一管理任意应用，仍需具备相应能力的内核或接管层。自动扫描程序和查找监听端口都不能替代流量接管。

## 必须保留的边界

- **入口和出口不同**：连接 `127.0.0.1:7890` 只说明进入一个本机代理入口；对方可能根据自己的规则直连。不能据此展示“强制远端代理成功”。
- **管理口和代理口不同**：Mihomo 控制 API 用于管理；HTTP/SOCKS5 用于承载流量。不能拿任意代理端口尝试管理写入。
- **直接联网不是全局绕过**：接管组件放行的连接仍可能受到系统代理、其他 TUN 或 VPN 影响。状态必须反映实际观测。
- **UDP 需要端到端能力**：不能从 HTTP 可连接推出 UDP 可用；SOCKS5 也要验证 UDP 支持及中间接管链路。
- **进程身份可能丢失**：嵌套代理、辅助进程或不同权限会影响识别；必须测试实际应用连接。
- **现有长连接不会自动变更**：规则修改后要检查新连接，不能只根据保存结果宣布成功。
- **防止回环和重复接管**：后续端口路线须验证自身、代理内核、DNS 和本地管理连接的排除规则，以及与现有 TUN/系统代理的协调。

以上条件由能力探测和状态说明表达，遇到未知条件先显示未验证。首版不通过静默改系统代理、启用额外 TUN 或结束所有连接来掩盖问题。

## 支持矩阵

| 后端组合 | 当前代码 | 下一步验证 |
| --- | --- | --- |
| Clash Party 2.0.4 + Mihomo v1.19.32 | Windows 标准模式、稳定内核；真实应用/恢复与连接观测 | 首次登记后重新打开；真实重启、订阅切换仍待验收 |
| 其他 Mihomo 客户端 | 架构扩展点 | 确定具体客户端与版本，再适配配置所有者 |
| 独立 Mihomo | 架构扩展点 | 控制端点、长期配置归属、进程接管 |
| sing-box | 类型候选，未实现 | 不同配置/控制能力、进程识别、重载 |
| HTTP/SOCKS5 + 接管组件 | 类型候选，未实现 | 组件选择、许可证、权限、TCP/UDP、冲突和回环 |
