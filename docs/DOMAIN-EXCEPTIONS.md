# 按应用域名例外

在应用详情中选择“编辑例外”，添加域名、匹配方式和联网方式，核对后点击“应用例外”。取消或 Esc 只关闭编辑窗口，不修改规则。每个应用最多 20 条，必须先设为直连或跟随代理组，并有已核实的精确程序路径。

## 匹配顺序

1. 精确域名优先，随后按域名后缀长度从长到短匹配。
2. 后缀包含域名自身及其子域名；`example.com` 不匹配 `badexample.com`。
3. 每条例外同时匹配该应用的精确主程序/辅助路径与域名；不生成全局域名规则。
4. 未命中例外时使用该应用的基础联网方式，其他应用继续原规则。

只接受域名，不接受 URL、端口、IP、通配符或自定义规则表达式。国际域名使用 punycode。路径含不能配对的括号时拒绝生成组合规则；不会修改程序或安装目录来绕过限制。

## 代理与恢复

代理例外绑定当前统一代理组，更换统一组时同步迁移。组内切换由 Mihomo 处理；组选择 DIRECT 时仍然是直连。例外的组消失时生成 REJECT，避免基础直连规则接住本应代理的目标；基础规则仍使用原有失效策略。

新增、修改、移除通过现有 `RoutingService.applyAutomatically`：核对 revision、所有权和运行规则，准备备份与独立守护，校验配置、重载、复查、确认；失败恢复上一份设置。断开、旧预览、共享系统宿主、无效身份不能写入。按原规则会移除本应用的专属设置及例外。

当前临时分流与域名例外不能同时使用，须先结束期限或明确移除例外。例外变更记录在操作记录中，通过详情或备份预览恢复，不宣称可进行普通联网方式的单步撤销。

## 保存、导入和证据

普通联网选择与辅助进程更新保留例外；程序重绑随原身份迁移并重新核对路径。设置导出、升级备份和历史备份包含白名单域名及模式，不携带控制凭据。导入预览显示例外差异，代理例外使用预览中的当前绑定组；老文件缺少例外字段时保留当前例外，显式空列表才清除。场景方案只保存联网模式，不复制域名例外。

应用诊断同时检查域名命中的 AND 规则及出口链；只命中应用基础规则不算该例外已验证。未观察到新连接仍显示待观察。

实现入口为 `src/core/domainExceptions.ts`、`src/core/managedRouting.ts` 和 `src/main/services/routingService.ts`。即时规则与持久化覆写共用生成函数。组合规则及规范化 payload 参照 [Mihomo 官方规则说明](https://wiki.metacubex.one/config/rules/)和 [v1.19.32 逻辑规则实现](https://github.com/MetaCubeX/mihomo/blob/v1.19.32/rules/logic/logic.go)。

隔离真实内核验收覆盖精确优先、后缀、其他域名、另一进程访问同域名及恢复原规则。代理组在夹具中选择 DIRECT，仅证明选择链和作用范围，不代表远端代理节点或真实订阅刷新验收。
